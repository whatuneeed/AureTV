# 13 — Адаптивные раскладки HD → 4K

Дата: 11.11.2026. Выпуск: `0.4.40` (vc60). Статус: **PASS** для объёма этапа 7 (UX-18, UX-25); `NOT TESTED` — §6.

Все числа ниже — `MEASURED` на эмуляторе `hume-tv` (API 34, панель 1920×1080, 320 dpi). Реальный ТВ и 4K-растеризация не проверялись и результатом эмулятора не выдаются.

---

## 1. Дефект до этапа 7

- Масштаб считался только по ширине: `screenWidthDp / 1920`. Высота окна не читалась вовсе, поэтому панель шире 16:9 (21:9 и подобные) получала канву выше окна и обрезала док и нижний ряд по вертикали.
- Канва не центрировалась: на окне не 16:9 остаток высоты уходил одной полосой вниз.
- `WindowInsets.safeDrawing` не учитывались: вырез или временная системная полоса могла лечь поверх верхней капсулы.
- Поля 50 и 90 pt были двумя независимыми числами (UX-25): связь «кромка дока ближе к краю, чем кромка сетки» нигде не была записана.

## 2. Решение

**Формула** — `TvMetrics.kt:104-109`:

```kotlin
internal fun tvCanvasFactor(widthDp: Float, heightDp: Float): Float {
    if (!widthDp.isFinite() || !heightDp.isFinite() || widthDp <= 0f || heightDp <= 0f) {
        return 1f
    }
    return minOf(widthDp / TvOs.SCREEN_WIDTH, heightDp / TvOs.SCREEN_HEIGHT)
}
```

Меньшая ось побеждает: широкое окно получает поля по бокам, высокое — по вертикали, 16:9 сводится к прежнему правилу по ширине. Неограниченный размер (превью, тестовый хост) сохраняет масштаб 1.

**Хост** — `ui/TvCanvas.kt:27`:

- `BoxWithConstraints(fillMaxSize + windowInsetsPadding(safeDrawing))`, выравнивание `Center`;
- внутри — `Box(requiredSize(1920·factor, 1080·factor))`;
- `CompositionLocalProvider(LocalTvScale provides TvScale(factor))` — все экраны берут масштаб из канвы, а не считают его сами.

`rememberTvScale()` (`TvMetrics.kt:116-122`) сначала читает `LocalTvScale`; вне канвы (юнит-тесты, превью) падает на `LocalConfiguration`. Один источник масштаба на всё дерево.

**Активности.** Все три поверхности обёрнуты в канву, окно отдано контенту целиком:

| Активность | `setDecorFitsSystemWindows(false)` | `TvCanvas` |
|---|---|---|
| `MainActivity` | :77 | :117 |
| `SettingsActivity` | :40 | :50 |
| `SetupActivity` | :39 | :48 |

Фон окна `#0E0E11` совпадает с нижним цветом градиента, поэтому поля не читаются как отдельная рамка.

**UX-25** — `TvMetrics.kt:24-33`: контентное поле одно — `SAFE_AREA = 90`. Полоса дока сознательно заходит на 40 pt ближе к краю: `DOCK_BLEED = 40`, `DOCK_X = SAFE_AREA - DOCK_BLEED = 50`, `DOCK_WIDTH = SCREEN_WIDTH - DOCK_X * 2`. Отношение закреплено тестом, а не комментарием.

**Попиксельные сверки** (`PIL`, разница в шкале 0–255):

- `03` против `01`, уменьшенного до 1280×720: средняя абсолютная разница **1.35**, горизонтальные полосы (капсула, заголовок, док, второй ряд) совпадают в пределах **2 px**. 16:9 рендерится как точный даунскейл 1080p.
- `04` (плотность 160 dpi → окно 1920×1080 dp) против `01`: средняя разница **0.38**, отличия только в полосе часов и погоды (48–124 px) — геометрия канвы в дизайн-точках и в половинном масштабе идентична.
- После возврата `wm size reset` / `wm density reset` кадр Главной снова совпал с `01` (разница **0.38**, только полоса часов).

**4K.** `wm size 3840x2160` на этом образе не применяется: панель сообщает единственный режим 1920×1080, override не сохраняется. Поэтому 4K-раскладка подтверждена формулой (`tvCanvasFactor(3840, 2160) = 2.0` — юнит-тест) и прокси `04` (те же дизайн-точки при плотности 1×); 4K-растеризация 2× — `NOT TESTED`.

## 5. Тесты

- `TvCanvasFactorTest` — 5 тестов: 16:9 (1.0 / 0.5 / 2.0), меньшая ось (21:9 → 1.0, 4:3 → 1024/1920), safe area (1920×1000 → 1000/1080), неограниченное окно → 1.0, инварианты дока (`DOCK_X = SAFE_AREA − DOCK_BLEED`, `DOCK_WIDTH` замыкает ширину, док и шесть колонок помещаются).
- Обратный откат формулы на «только ширина»: падают `theShorterAxisLimitsTheCanvas` и `safeAreaInsetsShrinkTheFit`; с `minOf` зеленеют.
- `TvCanvasTest` (инструментальный) — канва 16:9 с точностью ±0.01 и границы канвы не выходят за корень.
