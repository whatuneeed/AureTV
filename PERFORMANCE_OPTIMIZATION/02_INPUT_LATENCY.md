# 02 — INPUT LATENCY (обработка пульта)

**Оценка: хорошая, с двумя замечаниями.** Input-архитектура — одна из сильнейших частей проекта.

## 2.1 Как устроен путь ввода

Единая точка — `HomeScreen`:
- `.onPreviewKeyEvent { … }` — любой KeyDown сбрасывает idle-таймер заставки (`onUserActivity()`), не потребляя событие.
- `.onKeyEvent { … }` — основной диспетчер: `Key.DirectionCenter/Enter/NumPadEnter`, `DirectionUp/Down/Left/Right`, `Back`, `Menu`, `Search/Assist`.
- `TvKeyRepeat` (`ui/components/TvKeyRepeat.kt`) владеет повтором вместо системы.

### Ключевое : `TvKeyRepeat`

```kotlin
fun firstPress(event: KeyEvent): Boolean {
    if (event.nativeKeyEvent.repeatCount > 0) return false
    return previous == null || time - previous > STALE_MS   // 1200 мс
}
const val REPEAT_DELAY_MS = 400L   // пауза перед авто-повтором стрелки
const val REPEAT_INTERVAL_MS = 100L // шаг повтора
```

- Система на Android повторяет удержанную клавишу ~30 раз/с **без начальной паузы** — это ломало таймеры long-press (OK). Здесь повтор «свой»: 400 мс пауза, затем 100 мс/шаг.
- `isOneShot(key)` — «однособытийные» клавиши (стрелки, OK/Enter, Back/Menu/Search) глотают повтор, пока не пройдёт `firstPress`. Это устраняет двойную обработку.

**Вывод:** потеря нажатий и «двойная обработка» систематически закрыты. Это намеренное, документированное решение.

## 2.2 Тайминги нажатий

| Константа | Значение | Назначение |
|---|---:|---|
| `EDIT_HOLD_MS` | 350 мс | удержание OK → режим редактирования |
| `FOLDER_HOLD_MS` | 750 мс | удержание на соседе → создание папки |
| `FOLDER_CONFIRM_MS` | 300 мс | подтверждение слияния в папку |
| `FOCUS_SAVE_MS` | 400 мс | дебаунс сохранения фокуса |
| `TvKeyRepeat.REPEAT_DELAY_MS` | 400 мс | пауза перед повтором стрелки |

**Потенциальная точка задержки:** комментарий в коде: *«Android reports a hold as ~500 ms with releases that can land near 430 ms, so 350 ms is a safe project value»*. То есть 350 мс — компромисс между «не рано зайти в edit» и «не поздно». Кандидат к проверке на реальном пульте: не ощущается ли вход в edit «вязким».

### P-INPUT-1 — двойной `delay` при возврате фокуса

`HomeScreen.kt` (~строка 850):
```kotlin
delay(60)
...
requester.requestFocus()
delay(350)
requester.requestFocus()   // второй раз «для TalkBack»
```
- Первые 60 мс — «после первого layout». Второй запрос через 350 мс — обход того, что TalkBack ставит свой first-node фокус при входе в окно.
- **Риск:** если пользователь нажал стрелку в эти 350 мс, визуального отклика по фокусу может не быть до истечения таймера. Для зрячего пользователя это ощущается как «залипание» после закрытия панели.
- **Проверить:** на ТВ закрыть панель и сразу нажать вправо — есть ли отклик < 100 мс. Если нет — `P-INPUT-1` подтверждён.
- **Кандидат фикса (STAGE 4):** не «слепой» повтор, а подписка на `focusState`/первый реальный key event; либо уменьшить второй delay и делать запрос по факту смены окна.

## 2.4 Конфликты обработчиков

| Механизм | Разрешение |
|---|---|
| OK «два края» (KeyDown+KeyUp) | `okDown` + `longPressHandled` — релиз не запускает плитку, если нажатие «съел» другой экран |
| Back на гриде vs Activity | BackHandlers на гриде + панели; Activity Back подавлен (`OnBackPressedCallback`) |
| PreviewKeyEvent vs onKeyEvent | Preview только сбрасывает idle, не потребляет → панели и меню получают клавишу |
| Захват фокуса заставкой | `SaverScreen` берёт фокус на первом кадре, `onPreviewKeyEvent` закрывает по любому нажатию |

**Найденное исправленным в коде:** `FIXES.md #6` — «После прогона UI-тестов пропали фокус, полка или язык» → защита повторным запросом. Это и есть причина `delay(350)`.
